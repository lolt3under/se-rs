# Performance notes

These are measurements from one laptop, against the BSD tools shipped with
macOS. They describe the tested workloads; they are not a blanket promise that
`se` beats every sed, grep, awk, or ripgrep build.

Run `scripts/bench.sh` to repeat the comparison on the same machine or collect a
new set of results elsewhere.

## Test machine and method

| Item | Value |
|---|---|
| Machine | Apple M1 Pro, 8 cores |
| OS | macOS, Darwin 24.6.0, `aarch64-apple-darwin` |
| Build | release profile, fat LTO, one codegen unit, `target-cpu=native` |
| Input | 1.47 GiB synthetic log generated by `scripts/bench.sh` |
| Baselines | `/usr/bin/sed`, `/usr/bin/grep`, `/usr/bin/awk` |
| Samples | five runs per command |
| Reported value | minimum wall time |
| Output | redirected to `/dev/null` |

The minimum answers a narrow question: how fast can this workload run when the
machine is otherwise quiet? It does not show variance, cold-start distribution,
energy use, or throughput under contention.

`se` applies `F_NOCACHE` to directly mapped files on macOS and gives the kernel
`MADV_SEQUENTIAL | MADV_WILLNEED` hints. The BSD tools may read from a warm page
cache while repeated `se` runs ask the system not to retain the same data. That
makes the comparison unusual. It is recorded here so a future benchmark does
not quietly change the I/O conditions.

## Recorded results

| Workload | se | macOS tool | Ratio on this run |
|---|---:|---:|---:|
| Global literal substitution, `s/foo/bar/g` | 1.40 s | sed 14.7 s | 10.5x |
| Locate literal `ERROR` and print offsets | 0.38 s | grep 4.3 s | 11.3x |
| Keep lines containing literal `ERROR` | 0.40 s | grep 3.3 s | 8.3x |
| Keep lines containing literal `ERROR` | 0.40 s | awk 61 s | 152x |
| Reject lines containing literal `ERROR` | 0.87 s | grep 5.6 s | 6.4x |

GNU grep and ripgrep were not part of this run. Both are serious optimized
baselines and may narrow or reverse some results. Do not repeat the ratios above
as "faster than grep" without the macOS qualification.

## Why literal substitution is the strong case

A pattern with no regex metacharacters compiles to `SimdLiteralMatcher`. On
AArch64 it compares 16 bytes at a time with NEON and verifies candidate starts
against the literal. Other targets use the scalar/SWAR fallback.

Each substitution records a `Mutation { start, end, replacement }`. A literal
replacement is stored once in an `Arc<[u8]>` and cloned into each mutation, so
there is no separate replacement-buffer allocation per match. The mutation
vector itself still grows with the number of matches.

After the scan, the stitcher writes original spans and replacement spans in
order. A normal left-to-right substitution produces ordered mutations, which
avoids a sort.

## The fused line filter

The explicit line idiom:

```text
x/.*\n/ g/ERROR/ p
```

and the short line predicate:

```text
/ERROR/
```

are recognized by the parser optimizer when the filter is safe to fuse. The
literal version scans the input buffer for `ERROR`, then extends each hit
backward and forward to line boundaries. After emitting a line, it resumes at
that line's end, so repeated hits on one line do not produce duplicate output.

The scan still examines the input. Its matching cost is linear in input bytes;
only the work of constructing and filtering a view for every line is avoided.
Line-boundary work grows with selected lines rather than all lines.

An inverted filter must account for every line, so it enumerates lines and
rejects those containing the literal. It is still fused, but it cannot skip
nonmatching records the way a keep filter can.

Case-insensitive plain literals use the regex meta engine's Unicode folding in
a similar search-and-extend path. General regex filters remain on the per-view
pipeline unless the optimizer can prove the transformation preserves line
semantics.

## Memory behavior

Memory depends on the program:

- read-only selectors over a mapped file borrow input ranges;
- stdin uses a 4 MiB anonymous mapping and spills larger input to a temporary
  file that is then mapped;
- `s///g` and `c//` store one mutation record per selected edit;
- capture replacements allocate their rendered bytes per match;
- `r//` allocates the full reduced result;
- awk stores variables, fields, and associative arrays in owned memory.

Dense substitution is therefore `O(number of matches)` in memory, not `O(1)`.
On a multi-gigabyte file with a one-byte pattern, the mutation list can become
the limiting resource before scan speed matters.

## Reproduce the benchmark

The script is macOS-oriented because its baselines and file-size command are
the BSD versions:

```sh
scripts/bench.sh 1
```

The argument is the requested size in GiB. The generator writes a deterministic
seed log under `${TMPDIR:-/tmp}/se_bench.log` and doubles it until it reaches
the requested size. Existing data at or above that size is reused.

Before publishing a new table:

1. record the exact commit, compiler, machine, OS, and power mode;
2. state whether `target-cpu=native` was used;
3. include GNU grep and ripgrep if the claim mentions them;
4. report all samples or at least a dispersion measure, not only the best run;
5. verify command outputs before timing them;
6. keep the generated input or its generator stable.

The current table remains useful as a regression baseline for the original M1
Pro workload. It is not a substitute for benchmarking the data and toolchain a
new user actually has.
